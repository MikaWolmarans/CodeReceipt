# Manual sections

The canonical section set, ported from CodeReceipt's synthesis schema. Use these
for every file. `AGENTS.md` and `CLAUDE.md` use the terse form (identical content
in both); `MANUAL.md` expands each one. Omit any section you genuinely can't
support from the code (don't pad). Do not use em dashes or en dashes anywhere.

## AGENTS.md / CLAUDE.md (agent context, terse, identical content)

```markdown
# {repo_name}: Agent Context

> Auto-generated by CodeReceipt. Drop this in the repo root so AI tools
> understand the codebase before they touch it. Works with any agent that reads
> AGENTS.md or CLAUDE.md (Claude Code, Cursor, Windsurf, Copilot, Zed).

## Project Overview
{1 to 2 sentences: what this project is.}

## Architecture
{2 to 3 sentences: how it's structured and how data flows. A "User, Frontend,
API, Database" line if it applies.}

## Key Systems
- **{system}**: {what it does}. Main files: `{paths}`. If it breaks: {consequence}.

## Safe to Touch
{The four traffic-light lists, see safe-to-touch.md.}

## Environment Variables
- `{NAME}`: {purpose} {(required)/(secret) if known}   (names and purpose only, never values)

## Known Risks
- {risk and why it matters}

## Conventions
- {a rule the codebase follows that an editor should respect}

## AI Handoff Notes
{Anything an AI agent should know before editing: gotchas, non-obvious coupling.}
```

Write this content to **both** `AGENTS.md` and `CLAUDE.md`. Keep the wording
tool-agnostic ("the agent", not "Claude").

## MANUAL.md (human owner's manual, fuller)

Same spine, expanded into readable prose. Recommended order:

1. **What You Built.** 1 to 2 plain sentences, then a **Quick Start** block:
   what it does, who uses it, the primary user flow, the main moving parts, and
   what to understand before editing.
2. **Architecture.** How the pieces fit. Name the frontend, backend, database,
   auth, APIs, hosting, and external services only where the code shows them,
   otherwise "Not confidently detected."
3. **Key Systems.** Per system: what it does, main files, what it depends on,
   what breaks if it fails, how to edit it safely, and a risk level
   (low, medium, high, critical).
4. **Safe to Touch.** The four traffic-light lists (see safe-to-touch.md).
5. **Environment Variables.** Name, purpose, required?, secret?, what breaks if
   missing. Never values.
6. **Running Costs.** Only services actually evidenced in the code: what each
   powers, what to monitor, what happens at the limit, and a cost-risk rating.
   If none are evident, say so.
7. **Known Risks.** The honest register of what could bite them.
8. **Suggested Next Actions.** A short checklist of concrete improvements.

Close with a one-line confidence statement (high, medium, or low) and a note that
the manual reflects the code as scanned, not runtime behaviour.
